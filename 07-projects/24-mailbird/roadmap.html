ADR-0006 · Product name #

From docs/decisions/0006-product-name.md in snds/Mailbird, as of 45efcc1 · Open on GitHub

Read it here
  • Status: Open. Owner decision needed.
  • Date: 2026-10-13

Context

Mailbird is a live commercial email client from Mailbird, Inc. It ships on Windows and macOS with freemium pricing, so the name collides with an active trademark in our exact category.

Decision so far

  • "Mailbird" is a working repo name only.
  • Package and crate names are kept neutral where it's cheap:
    • Rust core: pim-core.
    • Shell: mailbird-shell. Rename it with the product.
  • The app bundle identifier design.snds.mailbird must change before any store submission.

To do before any public release

  1. Choose a name.
  2. Run a trademark search (USPTO and EUIPO, class 9/42).
  3. Check domain and store availability.
  4. Rename the repo, productName, identifier, and index.html title.

Google sign-in and verification #

From docs/google-verification.md in snds/Mailbird, as of 45efcc1 · Open on GitHub

Read it here

Gmail, Google Calendar, and Google Contacts sign in with OAuth (see ADR-0013). Google requires every app that does this to be registered, and an app that reads Gmail to be verified before the public can use it. This page covers both:

  • Using your own OAuth client. Works today, for you and up to 100 test users.
  • The verification checklist. Needed before the app ships with a built-in client for everyone.

Google renames these console screens often. The steps say what each screen is for, so you can find it even if the label changes.

Use your own OAuth client

  1. Create a project in the Google Cloud console.
  2. Enable these APIs (APIs & Services → Library):
    • Gmail API
    • CalDAV API
    • Google Contacts CardDAV API
  3. Set up the consent screen (Google Auth Platform):
    • User type: External.
    • Branding: your app name and support email.
    • Data access: add these scopes:
      • https://www.googleapis.com/auth/gmail.modify
      • https://www.googleapis.com/auth/calendar
      • https://www.googleapis.com/auth/carddav
      • openid, email, profile
    • Audience: leave the app in Testing and add your Google address as a test user.
  4. Create the client (Clients → Create client):
    • Application type: Desktop app.
    • Copy the client ID and client secret.
  5. Add it to the app: Accounts → Gmail → paste both → Save client → Continue in browser.

What to expect while the app is in Testing:

  • A warning page. Google shows "Google hasn't verified this app". Choose Continue (it may be under Advanced) only for a copy of the app you built or trust.
  • Weekly sign-in. Google expires refresh tokens for Testing apps after 7 days. The account then shows Sign in again; one click reconnects it, and no mail is lost.
  • Test users only. Only the test users you listed can sign in.

Bake a client into a build

To ship a build with a client, set these at compile time:

MAILBIRD_GOOGLE_CLIENT_ID=… MAILBIRD_GOOGLE_CLIENT_SECRET=… pnpm tauri build

A client someone adds in the app always takes precedence over the built-in one.

Why these scopes

Scope Google's class What the app does with it
gmail.modify Restricted Reads mail, and sets read, starred, and archived labels. It also sends mail through the Gmail API, so no SMTP password is needed. It cannot delete mail permanently, which the narrower scope rules out.
calendar Sensitive Reads and writes your calendars over CalDAV, including invitations and reminders.
carddav Sensitive Reads and writes your contacts over CardDAV.
openid email profile Non-sensitive Your name and address for the account list.

gmail.readonly + gmail.send would be narrower, but they can't archive or mark mail read, which the app needs.

Verification checklist (before a public release)

Verification of a restricted scope is Google's longest review. Plan for weeks, not days.

  • A verified domain. The homepage and privacy policy must be on it (Search Console verification).
  • A homepage that describes the app and links to the privacy policy.
  • A privacy policy that names the Google data used, says where it's stored (on the device only), and includes Google's Limited Use statement.
  • Scope justifications: one paragraph per scope, matching the table above.
  • A demo video (unlisted on YouTube). It should show:
    • the consent screen with the client ID visible;
    • each scope in use (archive, read, send, a calendar edit, a contact edit);
    • account removal revoking access.
  • Brand review: the app's name and logo can't suggest it's Google's. This depends on the rename in ADR-0006.
  • Security assessment:
    • Restricted scopes normally require an annual third-party assessment (CASA).
    • Apps whose restricted data never leaves the user's device can qualify for an exemption. The desktop and mobile apps are built that way: mail goes from Google straight to the device, and no server of ours sees it.
    • Ask for the exemption during verification and confirm the current rule then.
    • A hosted web gateway would not qualify (ADR-0004).
  • Publish the consent screen (Audience → Publish app) only after approval.

What the app already does for verification

  • Sign-in happens in the system browser (RFC 8252), never in an embedded webview. It uses PKCE and a loopback redirect on 127.0.0.1.
  • Tokens live in the OS keychain. Mail stays in the local database. Nothing goes to a server of ours.
  • Removing an account revokes its tokens with Google before deleting them.
  • The sign-in screen lists, in plain words, what Google will ask for.

Microsoft sign-in setup #

From docs/microsoft-setup.md in snds/Mailbird, as of 45efcc1 · Open on GitHub

Read it here

Outlook.com, Hotmail, and Microsoft 365 accounts sign in with OAuth, and mail, calendars, and contacts go through Microsoft Graph (see ADR-0014). Microsoft requires every app that does this to be registered. This page covers:

  • Registering your own app. Works today, for personal and work or school accounts.
  • Publishing for everyone. What a public release needs.

Microsoft renames these screens often. The steps say what each one is for, so you can find it if the label changes.

Register your own app

  1. Open App registrations in the Microsoft Entra admin center → Applications → App registrations → New registration.
    • A free personal Microsoft account works. Microsoft creates a directory for you on first visit.
  2. Name: anything, for example "Mailbird (personal)".
  3. Supported account types: Accounts in any organizational directory and personal Microsoft accounts.
  4. Redirect URI:
    • Platform: Public client/native (mobile & desktop).
    • URI: http://localhost. Microsoft ignores the port for localhost, and the app picks a free port each time.
  5. Register, then copy the Application (client) ID from the Overview page.
  6. Authentication → Advanced settings: turn on Allow public client flows.
    • There's no client secret to make. An installed app can't keep one, and PKCE protects the sign-in instead.
  7. API permissions → Add a permission → Microsoft Graph → Delegated:
    • Mail.ReadWrite
    • Mail.Send
    • Calendars.ReadWrite
    • Contacts.ReadWrite
    • offline_access, openid, email, profile (usually already there as User.Read's companions)
  8. Add it to the app: Accounts → Outlook / Microsoft 365 → paste the ID → Save app registration → Continue in browser.

What to expect:

  • A consent page listing the permissions above. Personal accounts approve it themselves.
  • Work or school accounts may need an administrator to approve the app first ("Need admin approval"). That's the organization's policy, not an error in the app.
  • Your account picker. The app asks Microsoft to let you choose the account, so a browser signed in to several doesn't pick one silently.
  • Sign-ins last. Microsoft refresh tokens are renewed on each use. An account that sits unused for about 90 days, or whose password changes, shows Sign in again.

Bake a registration into a build

MAILBIRD_MICROSOFT_CLIENT_ID=… pnpm tauri build

A registration someone adds in the app always takes precedence over the built-in one.

Removing an account

Microsoft has no way for an app to revoke its own sign-in. Removing the account deletes its tokens from this device. To revoke access everywhere:

  • Personal accounts: account.live.com/consent/Manage.
  • Work or school accounts: myapps.microsoft.com → the app → Revoke.

Why these permissions

Permission What the app does with it
Mail.ReadWrite Reads mail, and sets read, flagged, and archived (a move to the Archive folder). It never deletes mail.
Mail.Send Sends the message the app built, as MIME, so Outlook files the Sent copy itself.
Calendars.ReadWrite Reads and writes your calendars, one-off edits to recurring events, and replies to invitations.
Contacts.ReadWrite Reads and writes your contacts.
offline_access openid email profile Keeps you signed in, and shows your name and address in the account list.

Publishing for everyone

Unlike Google's restricted Gmail scopes, these permissions need no security assessment. A public release needs:

  • One registration for the app, baked into release builds.
  • Publisher verification: a Microsoft Partner Network account tied to a verified domain. Without it, the consent page says "unverified".
  • A homepage and privacy policy linked from the registration's Branding page. They depend on the rename in ADR-0006.
  • Optional, for organizations: Microsoft 365 app certification. Some admins require it before approving an app.

ADR-0054 · The menu-bar mini calendar (Phase 42) #

From docs/decisions/0054-menu-bar-calendar.md in snds/Mailbird, as of 45efcc1 · Open on GitHub

Read it here
  • Status: Accepted. The parts that need a real desktop wait on a hardware check (see the checklist below).
  • Date: 2026-10-17
  • Builds on: ADR-0010 (calendar, quick add), ADR-0016 (one dispatcher, a Host per platform), ADR-0030 (Join)

Fantastical and Itsycal earned their place by answering "what's next?" without opening a calendar. This phase puts that in the desktop menu bar on macOS, and in the tray on Windows and Linux.

Decisions

An icon, a line of text, and a small window

  • The icon is a calendar glyph:
    • On macOS it's a template image, so the menu bar draws it in its own ink, light or dark.
    • On Windows and Linux it's the app icon, which holds up on any taskbar.
  • Beside the icon, the next event in a few words: "Design review in 25 min", "Standup now". This is on by default, and a switch turns it off for just the icon.
    • It shows in the macOS menu bar and on Linux panels that show a label.
    • Windows trays have no room for text, so the same words go in the icon's tooltip there.
  • A click opens the mini calendar under the icon, or above it when the taskbar is at the bottom. Clicking away closes it. It's 360×600 and has:
    • today's date;
    • Next up, with its time, place, and Join;
    • the month, with a dot on every day that has something;
    • the picked day's events (a click opens the event in the app);
    • quick add ("Coffee with Marcus today 4pm"), the same field as in Calendar.
  • Right-click gives Open Mailbird, New event…, and Quit Mailbird.

What "next" means

  • The rule: the event on now, or else the next to start in the next 12 hours. An event starting within 5 minutes beats the one that's on now, because that's the one you need to leave for.
  • Not counted: all-day events and birthdays. They'd crowd out the meeting you're about to miss.
  • Relative words ("in 25 min", "in 2 h 5 min", "now"). They need no clock format or time zone, and they read the same in every locale. The menu bar is brought up to date every 30 seconds.
  • One rule, written twice: pim_app::menu_bar::next_up for the menu bar, and nextUp in the web panel. The Rust tests and the browser suite check the same cases, so the two can't drift silently.

Closing the window keeps Mailbird running

  • While the menu-bar calendar is on, closing the main window hides it. Mailbird stays in the menu bar or tray, so the calendar and reminders keep working. This is how menu-bar calendars behave, and it's spelled out under the switch in Settings.
  • Getting back: click the Dock icon (macOS), choose Open Mailbird from the tray menu, or click an event in the mini calendar. Quit is in the tray menu, and the usual quit shortcut still works.
  • Safety: closing only hides the window once the tray icon actually exists. A Linux desktop without a tray never ends up with a hidden window and no way back.

Where the logic lives

  • pim_app::menu_bar decides what to show:
    • the prefs (menubar.prefs, both on by default);
    • next up, and the words for it;
    • the tooltip.
  • The Host trait gains two hooks: menu_bar(state) and show_app(jump).
    • The desktop shell (src-tauri/src/menu_bar.rs) draws the tray, places the window, and brings the main window forward.
    • The gateway keeps the defaults: no tray, and a single window.
    • So nearly all of this is tested without a desktop.
  • The mini window is the same web app at ?mini. It opens events in the main window through show_app, which sends an app:jump event there.
    • In a browser (the demo, or the gateway) there's only one window, so the mini page opens the app page in its place, carrying the jump.
    • The main window opens the event, or the event editor for New event….
  • Settings: "Calendar in the menu bar" and "Show the next event's name" sit under Accounts and settings, wherever the app runs on a device (not through a gateway).

Verification

  • App (cargo test -p pim-app):
    • next up: what counts, the 12-hour window, the 5-minute handover, and the relative words;
    • long names are shortened;
    • the state follows the prefs.
    • Through the dispatcher: the prefs default on, a change reaches the host at once, and show_app carries its jump to the host.
  • Desktop shell: cargo check and clippy -D warnings pass on Linux with the tray feature. The macOS-only line (Dock reopen) can't be compiled here, because the sandbox has no Apple SDK.
  • Browser (phase42, 22 checks):
    • The mini calendar: today's date, next up "in 10 min", "Now" during the event, the next event within 5 minutes, tomorrow's first event late at night, and "Nothing else" on a quiet evening.
    • Using it: Join, picking a day, and quick add.
    • Opening the app: an event opens on that event, Open Mailbird opens the app, and New event… opens the editor.
    • Settings: both switches, and the second hides with the first.
    • Also: dark mode, and no console errors.
  • Regression: all earlier browser suites pass. tsc -b, oxlint, and vite build are clean. The ratchet is unchanged at 241 / 2 / 0 / 0.

To check on real hardware

These need a desktop session, which the cloud sandbox doesn't have:

Consequences

  • Closing the window no longer quits while the calendar is on. Anyone who wants the old behavior turns the switch off. The note under the switch says so.
  • Two copies of the next-up rule (Rust and TypeScript), kept honest by matching tests. Moving the panel's version to the core would cost the demo its own copy.
  • Follow-ups: an icon that shows today's date, like Fantastical's; keyboard shortcuts to open the mini calendar from anywhere; and declined invitations dropping out of next up (occurrences don't carry your response yet).

Mobile device spike #

From docs/mobile-spike.md in snds/Mailbird, as of 45efcc1 · Open on GitHub

Read it here

The four exit criteria from ADR-0002, checked on real devices. Failing any of them moves mobile to Capacitor. The groundwork (ADR-0015) is done, so the spike only has to cover what needs a phone.

Devices: one iPhone (iOS 18 or later), and one Android phone with Google Play services. Optionally a second Android phone without Google, for UnifiedPush.

0. Build

  • macOS: Xcode, plus the Rust targets: rustup target add aarch64-apple-ios aarch64-apple-ios-sim.
  • Android: Android Studio, the NDK, and the Rust targets: rustup target add aarch64-linux-android armv7-linux-androideabi x86_64-linux-android.
  • Scaffold: pnpm tauri ios init and pnpm tauri android init in apps/web. The app runs and the inbox shows sample mail.
  • Add a real account (iCloud or Fastmail) and watch it sync.

1. Background sync

  • iOS: register a BGAppRefreshTask that calls the background_pass command. Debug it with e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"…"].
  • Android: schedule a periodic WorkManager job (15 minutes, the platform minimum) that calls background_pass.
  • Pass: send yourself mail with the app closed. Within one background run there's a local notification, and the message is in the inbox when you open the app.
  • Pass: a pass finishes within its 25-second budget on a slow network (finished: true in the result, or it stops cleanly).

2. Push

  • Relay up: start it with Docker on a server you own, behind https (tools/push-relay/README.md).
  • iOS:
    • Register for remote notifications, and pass the APNs token to set_push_target as {"platform":"apns","token":…,"sandbox":true} for a debug build.
    • Set up the relay with an APNs key.
    • Handle the background push by calling background_pass.
  • Android with Google: get the FCM token, then set_push_target with {"platform":"fcm","token":…}. On a data message, run background_pass.
  • Android without Google: register with a UnifiedPush distributor (ntfy) and enter its endpoint in the setting.
  • Pass: with the app in the background, new mail notifies within about 10 seconds:
    • for an IMAP account,
    • for a JMAP account,
    • for an Outlook account (needs RELAY_PUBLIC_URL).
  • Pass: Send a test arrives. A deleted app's token gets forgotten by the relay.
  • Note how iOS treats background pushes in Low Power Mode and after force-quit. This decides whether to add a Notification Service Extension.

3. Keychain

  • iOS: passwords and OAuth tokens save and survive a restart (keyring with apple-native).
  • Android: move to keyring 4 (Android Keystore). Same check.
  • Pass: removing the app removes its secrets. Reinstalling asks you to sign in again.

4. Scrolling and input

  • Long list: sync, or use the demo's ?bulk=10000, then scroll the inbox top to bottom with Instruments (iOS) or the GPU profiler (Android).
  • Pass: 60 fps on a mid-range phone, no dropped frames when a page loads, and swipe actions still work.
  • Keyboard: open the composer and type in the body.
  • Pass: the formatting bar and Send stay visible above the keyboard on both platforms, including with the keyboard's suggestion bar and after rotating.

Outcome

Record what passed, what didn't, and any workarounds in ADR-0002. Then either continue on Tauri mobile, or start the Capacitor fallback with UniFFI bindings to the same pim-core.
