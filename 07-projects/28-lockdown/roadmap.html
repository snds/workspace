  • D37Lockdown's vault, item, version and attachment keys use a Lockdown-owned envelope (vault::keys::WrappedKey, same shape and AAD discipline as identity's KeyEnvelope), because identity's Purpose and KeyRefKind stop at the App Data Key (02-model §13 q.2). Note: as built the dependency runs crypto → identity, the reverse of the table in 03-architecture §2. Plain version: Lockdown wraps its own keys the same way the identity crate does, and asks the crate to grow those slots later so there is one code path. #Audit item
    What this means

    Status: Accepted by default under D38; audit item

  • D39The local store is one plain SQLite file holding ciphertext only #Audit item
    What this means

    (closes 03-architecture §11 q.1). Tables schema_version, vaults (one VaultRecord per vault: the public VaultContext ids and the Vault Key wrapped under the persona's Lockdown App Data Key), items (the item envelope), heads (the manifest chain); every body canonical CBOR in a BLOB. WAL mode, synchronous=FULL, secure_delete; file 0600 in a 0700 directory; a newer schema_version is refused. The search index is built in memory after unlock and never written. No SQLCipher: there is nothing plaintext for it to protect, and a second key layer would be a second thing to get wrong. Plain version: the vault file is a box of locked boxes plus the signed table of contents; nothing readable is in it, so the file itself needs no extra lock.

    Status: Accepted by default under D38; audit item

  • D41What the Vault Key wrap is bound to. #Audit item
    What this means

    The Vault Key is wrapped under the persona's Lockdown App Data Key with associated data KeyPlace { profile_id, persona_id, vault_id, key_id = the Vault Key's id (= every head's vault_key_ref), purpose: vault, wrapped_by: { app-data, the App Data Key's id }, v: 1 }, and stored as the vault's VaultRecord beside its public context. Opening a vault needs that App Data Key from the identity and nothing else; an envelope that names another persona, vault or key is refused by name before decryption. Plain version: the vault's key is locked under the persona's Lockdown key with a label that says exactly which vault and persona it is for, so it cannot be moved.

    Status: Accepted by default under D38; audit item

  • D42Where rollback memory lives. #Audit item
    What this means

    HeadMemory keeps, per vault, the newest manifest seq and head hash this device accepted, plus the identity store's own Head (D26 left that to the app), in its own file remembered.cbor in Lockdown's data directory: never inside the vault file, so an old copy of the vault file put back cannot bring the old memory with it. Written through a temporary file and rename, 0600, forward-only (an older or different head at the same seq is refused). Vault::load refuses a store behind it with the existing "Rollback attempt blocked" error. Per device, never synced. Plain version: the app writes down the newest page number it has seen in a separate notebook, so swapping the vault file for an old copy is noticed.

    Status: Accepted by default under D38; audit item

  • D43What a load checks before trusting the file, and what a version signs. #Audit item
    What this means

    Vault::load verifies the whole head chain against the devices the identity knows, refuses a rollback, unwraps the Vault Key, and then checks every item against the newest signed head: the same set of item ids, each item's latest-version hash, state, revision and shredded flag as the head recorded; a disagreement is ManifestMismatch, shown as tampering, before any field is opened. The item header (item_id, vault_id, kind, schema_v, class, device_only) is now covered by every version's signature and hash (ItemHeader), because that check showed a store could relabel a login as a note or clear device_only without breaking anything. trashed_at stays outside (07-workspace §5 q.4). Plain version: before the app believes anything in the file, it checks that every item is exactly what the signed table of contents says, and an item's type can no longer be changed behind its back either.

    Status: Accepted by default under D38; audit item

  • D44Who signs heads and versions. #Audit item
    What this means

    The device keystore's Ed25519 key, the one in the identity's Device.device_pub, through a Signer trait (a bare key still works for tests and for a vault with no identity). On load, heads and versions are verified against the public key of every device in the identity's records, this device's own key always included; revoked devices stay in that set so history they signed before revocation still verifies, and refusing their new heads is the sync step's job (only the server sees order between devices). Plain version: the device signs with the same key the identity already lists for it, so other devices can check the vault's history without being told anything extra.

    Status: Accepted by default under D38; audit item

  • D45Which persona Lockdown opens when there are several #Audit item
    What this means

    (D13). In order: the one persona that already holds Lockdown keys; else the only persona; else the only personal-kind persona; else the person chooses by id or label (--persona), and the error lists them. Two personas already holding Lockdown data is also a choice, never a guess. Plain version: if only one persona has ever used Lockdown, that one; if there is only one at all, that one; if one is the personal one, that one; otherwise ask.

    Status: Accepted by default under D38; audit item

  • D46Lockdown's keys in the identity, and adoption on attach. #Audit item
    What this means

    One App Data Key and one Crown-Jewel Key per persona, made on first use and wrapped under the Persona Key with the app label lockdown (wrap_app_key / wrap_crown_jewel_key), found again with app_keys (the crate has no lister for crown-jewel keys, so Lockdown filters envelopes() by the same three facts: purpose, wrapper, label). A new vault wraps under the newest App Data Key; an existing vault names in its record the key it was wrapped under, and that one is opened. On attach, if no app manages the identity Lockdown sets Profile.manager = lockdown (spec §7); an identity another app manages is used as is and left to that app, since the crate lets only the manager change the profile. A root whose identity this device is not enrolled in is an error naming the handshake and the kit, never a second identity (D10). Plain version: Lockdown keeps two keys per persona inside the shared identity, labelled as its own, and takes over looking after the identity only when nobody else is.

    Status: Accepted by default under D38; audit item

  • D48What the vault file reveals without a key: #Audit item
    What this means

    item ids, each item's kind, class and state, the field *names* of each item (they sit in the per-field AAD, 02-model §4), and the signed manifest. Never a value: no site, title text, username, password, or note. Confirmed on a scratch vault by reading the SQLite file raw. This matches 02-model as written, and the incumbents leak the same or more. Plain version: a thief with the file learns "there is a login with a title and a username", not what they say. If the audit wants kind and field names hidden too, that is an item-envelope change, not a store change.

    Status: Accepted by default under D38; audit item

  • D49The OPAQUE suite and its stretching step. #Audit item
    What this means

    Account login is OPAQUE (RFC 9807) through opaque-ke 4.0.1: ristretto255 for the OPRF and the 3DH key exchange, SHA-512, and Argon2id as the key-stretching function at the desktop floor (64 MiB, 3 passes, 4 lanes) on every device, fixed by the suite rather than negotiated, because a login must give the same key on a phone and a laptop and OPAQUE carries no signed parameter record (the identity's signed Argon2id record governs the kit and account wraps, not this step).
