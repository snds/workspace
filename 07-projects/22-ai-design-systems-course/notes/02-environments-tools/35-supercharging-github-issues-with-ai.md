# Supercharging GitHub Issues with AI

**The Ch2 payoff.** Claude Code, from the Learning Git product repo, is asked to:

1. File an issue *here*: adopt **Eddie** for real, not an approximation of the brand.
2. File an issue *on Eddie*: crawl this site, compare to Eddie, flag gaps that would block an on-brand rebuild.

Both issues land, **cross-linked**. Product issue lists Eddie ingredients to use, what not to throw away, dependencies, acceptance criteria (and can follow house issue style). DS issue is an adoption-test: what Eddie already covers vs blockers (no inline-code atom, no compact segmented control matching the site’s push/pull switch, no semantic branded lists, missing motion/skip-link/anchor primitives, hero image required, etc.). Some “gaps” are by design; some are real backlog.

**Why it beats the old DS intake:** not a one-paragraph drive-by from a random product team. Context of the actual product, plus an MCP (**Eddie Brain**) plus the product repo, so the story is coherent across the org’s many repos.

**Non-coders:** you still want repo access. Ask questions, file issues, inspect — even if you never ship production code.

**For Sean:** this is Ch1’s “AI as mortar” made operational, and the missing piece of Centric intake — product work should open DS issues that carry product context, not a screenshot and a vibe. Pair with house issue templates.
